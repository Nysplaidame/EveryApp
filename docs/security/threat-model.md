# EveryApp threat model

Method: STRIDE per component (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). Source of requirements: spec section 14 (`docs/superpowers/specs/2026-11-06-ferry-suite-v1-design.md`).

Status: M1 components (Core, Engine, CLI) are modelled in full. All other components are marked "designed in M2+": the mitigations from spec section 14 are recorded here as binding requirements and must be refined into threats and tests when the component is built.

Keep this file current whenever a component or trust boundary changes. Each milestone gets a security-auditor review against it. Findings are fixed or recorded under "Accepted risks".

## Trust boundaries

| ID | Boundary | Untrusted side | Notes |
|----|----------|----------------|-------|
| TB1 | User and file system | File and folder names, paths, file contents, attributes, reparse points, ADS | Every path and name is hostile input. Other local users and processes can change the tree while we work (TOCTOU). |
| TB2 | CLI arguments and environment | Argument strings, response files, environment | Treated as input from a possibly less-trusted caller (scripts, shortcuts). |
| TB3 | Journal and job files on disk | Journal contents, job files, settings files | A file the user can edit, another process can corrupt, or an attacker could plant. Parsed defensively, with size limits. The job spec (sources, destination, mode, options) is untrusted: resume needs explicit confirmation (CLI prompt or `--yes`) after seeing the paths, the mode and every risky saved option, and a saved job that moves or replaces files gets a dry-run preview first. In a portable install (`portable.flag` next to the program) the jobs and logs live in the program's folder, which other accounts may be able to write (a shared folder or USB stick): resume then warns that other people may be able to change saved jobs. |
| TB4 | App and helper service (named pipes) | Pipe messages, pipe clients | Designed in M2+. |
| TB5 | Explorer process and helper | Anything Explorer hands over | Designed in M2+. |
| TB6 | Non-elevated and elevated | Any request that asks for admin work | Designed in M2+. The M1 engine refuses to run elevated (TokenElevation check) and no message may advise running as administrator: a path-based copier running elevated over user-controlled paths is a planted-link privilege-escalation risk. Elevated work belongs to the M2 helper. |
| TB7 | Network (updates, feeds, alert services) | Everything received, plus the transport | Designed in M2+. |
| TB8 | Build and release pipeline | Dependencies, GitHub Actions, contributors | Covered by the supply chain controls below. |

## M1 components

### Ferry.Core (shared library: paths, journal format, results, logging)

| STRIDE | Threat | Mitigation |
|--------|--------|------------|
| S | A path is crafted to look like it is inside the selected tree but resolves elsewhere (traversal, `..`, alternate separators, 8.3 names, `\\?\` and device prefixes, trailing dots and spaces). | One path-normalisation and containment check in Core, used by every caller. Rejects device paths, reserved names and anything that does not stay under the root after full resolution. Property and unit tests cover the cases. Names listed by the file system are untrusted too (a hostile share or user-mode file system can list `..\x`): the walk skips any child name that is not one plain name (holds `\`, `/`, `:` or a control character, or is only dots and spaces) with a plain problem, and as defence in depth every folder creation and every same-volume rename target must resolve strictly inside the destination. |
| T | A journal or job file is edited or truncated so that a resume acts on false state. | Every journal line carries a CRC; reading stops at the first bad, unknown or rule-breaking line and the file is truncated there (only the good lines before it are trusted). It never guesses. Each record kind is checked by one validator shared by append and load (safe relative paths only; a part record names its part and its target, in the same folder). At every use site a journaled path is joined to the root and must still resolve inside it, and a part file must have Ferry's own name shape (`name.<8 hex>.ferrypart`); anything else is ignored as corruption. The job spec in the header is untrusted: it is validated, and resume runs only after the user confirms its sources, destination, mode and risky options (see Ferry.Cli). The header carries a format version (`v1`); a journal whose version this build does not know is refused whole with a plain "made by a newer or unknown version" message, never read or acted on (record kinds are frozen for v1). Writes are append-only and flushed at defined points; part-file records reach the OS before the part exists, and a second record right after the part is created holds which object on disk the part is (volume serial and file id). |
| T | Time-of-check to time-of-use swap: a directory is replaced by a junction after validation. | Containment is checked at the moment of use on an opened handle, not only up front: a part file's final path (GetFinalPathNameByHandle) must be under the destination root's final path, and verified deletes compare id, volume, size, time and final path on the same handle that deletes. See Engine. |
| R | A destructive action happens and nobody can tell what or why. | The journal records each file done, skipped or failed and every part file. Overwrites and move-source deletes are not yet journaled as undo records and are not undoable in M1 (planned with the UI's undo in M2); the report lists every problem. |
| I | Logs or errors leak personal paths, user names, machine names or secrets. | Logging goes through one scrubber that masks the user profile path and known secret shapes. Secrets never go into messages, journals or settings. Exception messages shown to the user are plain and path-free where possible. |
| D | A huge or deeply nested path list, a very long path or a hostile journal exhausts memory or time. | Size, depth and length limits on every parser: journal lines are capped at 64 KB, a journal file over 4 GiB is refused (on resume and in the job list) instead of being loaded into memory, one file may have at most 64 part records and 64 part-identity records (a record past that is refused on append and ends the trusted part on load), and a settings file over 1 MiB is never read (it is kept as a backup and defaults are used). Streaming reads. Limits are tested. A job refuses to start when the journal's drive has under 50 MB free, so the journal cannot fill a disk unnoticed. |
| E | A parser bug lets a crafted file run code. | No dynamic code loading, no reflection-based deserialisation of untrusted data, no BinaryFormatter. Parsers are fuzz-tested (journal format first). |

### Ferry.Engine (copy, move and verify engine)

| STRIDE | Threat | Mitigation |
|--------|--------|------------|
| S | A destination or source that is a symlink, junction or mount point redirects writes outside the intended tree. | Links (name-surrogate reparse points) to folders and to files are not followed unless the user asked; by default they are skipped and listed when copying, and a move never follows them (same volume: the link itself is renamed; another volume: left in place and listed). An existing destination folder that is a link is refused ("a shortcut to somewhere else") and nothing is written through it. Every part file's final path is checked through its own handle and, if it left the destination, deleted through that handle. Cloud and dedup reparse files are ordinary data. A source folder swapped for a link after the walk cannot make the job copy files from elsewhere: the handle the copier opens must be the walked file (same file id and volume, asked through that handle) and, unless the job follows links on purpose, its final path must lie under the source root's final path; a mismatch fails the file as "changed" and nothing is written. A same-volume rename (file, folder or link) first checks that the item under the name is the walked one. |
| T | TOCTOU between check and copy: a file or directory is swapped while the job runs. | Writes go to a random part name created with CREATE_NEW and delete access; its final path is checked on its handle before data is written. A move deletes its source only through `DeleteVerified`: opened without following links, file id, volume, size and last-write time must match what was copied, and its final path must be under the source root; deletion is by disposition on that handle (POSIX semantics where supported). Emptied source folders go only if empty and still the walked folder (same check). Same-volume moves are pure renames (MoveFileEx without COPY_ALLOWED); "same volume" is the volume GUID, and if Windows refuses the rename as crossing volumes the file is copied, verified, then deleted as above. On FAT, exFAT and some SMB servers file ids are 64-bit or zero, so these identity checks rest mainly on size and last-write time there (2-second resolution on FAT); a zero id is never compared. |
| T | Overwrite or move destroys the only good copy if the job is interrupted. | Preview, then explicit confirmation. Move is copy, verify, then delete the source. Undo information is journalled. Interrupted jobs resume from the journal. |
| T | Silent corruption in transit. | Optional verification pass (hash compare). Failures are reported, and the source is never deleted after a failed verify. A small file is read back through its own unbuffered part handle before it closes (so from the drive, not the cache); a large one is reopened unbuffered after closing. The part handle has read access for this and still shares nothing. |
| T | A power cut leaves a small copied file blank or stale under its real name (copies skip forcing each file under 8 MiB to disk, for speed). | Moves, rescued files and reconnected files are always forced to disk before the rename (a move deletes its source). For a copy, the journal marks such files "not on disk yet". Because a power cut can also lose the journal's last records, a resumed copy checks the file it would have written for every item not trusted as done: if that file is this job's own it is read back and compared with its source, kept if it matches, otherwise replaced without a conflict question. "This job's own" means a plain file (not a link) inside the destination, in the same folder as the normal name (the journal's part record can only pick a renamed file there), the source's size, and either the very object one of the item's journaled part files was (its identity is journaled right after the part is created; a rename keeps it) or, under the item's normal name only, dated like the source or within the job's run (from its start to a minute after the journal was last written). Those dates come from the journal itself, so they never make a file under another name (such as "name (2).ext") this job's own. A file changed after the job stopped fails that test and goes through the user's conflict rule. A file that was renamed into place just before a crash is only looked for in the item's own folder. The journal stays untrusted: containment and name-shape checks as everywhere. See Accepted risks for a job that already finished. |
| T | A network drop loses acknowledged writes or redirects a reopened part file. | Retry reopens the existing part without truncating it or following a file link, and checks its handle's final path and file id (with volume) against the original part before writing, so a hard link to another file under the part's name is refused too. A redirected reopened file is left alone. After a write handle is reopened the entire part must match the copied data, even with verification off. A reopened source must keep its identity, size and write time, and its final path must still be inside the source root (so a swapped-in folder link is refused even on a file system that gives no file ids), checked on the reopened handle itself (not by name first). Several reads and writes may be in flight: one reopen per handle at a time, every other I/O on the old handle waits and runs again on the new one after the same checks, and once a reopen fails its check the handle stops for good (every queued and later I/O gets that failure; the name is never opened again). Buffers go back only after their I/O ends; a write still pending on a closed handle (its close timed out) can only land its own chunk at its own offset, and the full hash check then runs. |
| T | Rescued data is mistaken for a complete original, including after resume. | Lost sectors are zero-filled and listed in a warning and a separate report. A rescued move retains its source, does not count as verified, and does not journal clean completion. Reports use fresh contained part files and never overwrite existing reports. |
| D | A failed drive or disconnected share causes endless retries. | Rescue defaults to at most 4,096 lost sectors per file (configurable); only bad blocks trigger rescue. Network and sharing failures use cancellable exponential waits capped at 30 seconds each and five minutes total per operation, with no whole-file retry after exhaustion. With several chunks in flight the five-minute budget is per in-flight chunk (at most 4 per handle), all waiting on one reopen at a time. |
| R | Disputed outcome of a job. | Per-file result in the journal and the final report. |
| I | Copying leaks data via wrong permissions (new files more open than the source, or the destination readable by others), or loses the "downloaded from the internet" marker. | New files inherit the destination ACL by default. Copying permissions is opt-in, only between this PC's fixed drives, and filtered: entries for unknown or foreign accounts, OWNER RIGHTS, and every allow entry that gives a broad group (Everyone, Users, Authenticated Users, Anonymous, INTERACTIVE, Guests, or Domain Users, any domain's RID 513) any write or change right is dropped. That includes the generic rights GENERIC_ALL, GENERIC_WRITE and MAXIMUM_ALLOWED, which inherit-only folder entries often use (they are tested on the raw access mask, so they cannot slip past the specific-rights check); owner and list are written in one call; if the result would lock the user out it is reverted to inherited permissions, access is checked again after the revert, and if the user is still locked out (the folder itself passes down a deny) a plain warning is given. A same-volume move is a rename, so the item keeps its source ACL (as Explorer does). The mark-of-the-web stream (`Zone.Identifier`) is always copied; on a move, failing to copy it keeps the source. FAT and exFAT destinations, which cannot hold it, get one pre-flight warning. Other streams are opt-in, and only `:name:$DATA` names are accepted. |
| D | A tree with cycles, enormous file counts, sparse or special files, or a full disk hangs or fills the drive. | Cycle detection through reparse handling. Free-space check up front (destination and the journal's drive). Cancellation honoured at every stage, including stream copies. Temp files are cleaned up on failure. Special device files are skipped. Planning and copying are linear in the number of items (per-folder counts computed once, set lookups for skipped folders); a test plans 20,000 folders with 100,000 files in well under 2 seconds. The problem list keeps the first 10,000 entries and counts the rest. |
| E | Engine run by a privileged caller writes where the unprivileged user could not. | The engine itself never elevates and refuses to run elevated; the check it uses cannot be replaced through the public constructor. Elevated work (M2+) uses a per-job worker that revalidates every path against the requesting user's access. |
| T | Parallel copies (solid-state drives only, up to 8 at once) make two copies write one name, or let a conflict decision look at a half-landed file. | Every file is still decided one at a time in planned order; only the copy itself runs alongside others. A name chosen for a running copy is reserved: the next decision waits for that copy, the name search skips reserved names, and starting a second copy into a held name is refused outright (a bug, not an I/O error). Names the file system may read as another file (short 8.3 look-alikes, trailing dot or space) wait for every running copy in the same folder first. Part files, check, rename, journal order and move-deletes are unchanged per file. |
| D | Parallel copies leave work half-done or the journal closed too early, or an unbounded number of copies run. | The job waits for every copy to end before it closes its journal, reports finished or leaves the source of a move alone. A failure or a stop starts no new file and lets the running ones finish or be cancelled cleanly. A journal that cannot be written mid-job (disk full, I/O error) is such a stop: one plain problem ("the job's record couldn't be saved"), no new file and no new part file, nothing thrown at running copies, and the journal keeps only whole records so the job can be resumed. Never more than 8 copies; one at a time for hard drives, unknown drives, network targets, rescue mode and same-volume moves. |
| D | Parallel copies and large-file turns starve each other or ignore the user's speed limit. | One speed limit is shared by the whole job (not one per copy). Large files take turns to copy and to check, so a check can run behind the next copy without piling up. |

### Ferry.Cli (command-line front end)

| STRIDE | Threat | Mitigation |
|--------|--------|------------|
| S | A script passes arguments that impersonate another operation, such as a delete flag appended through string concatenation. | System.CommandLine plus an explicit option allow-list (variadic paths must not swallow unknown flags). Unknown options are errors. No shell invocation, and no argument is ever passed to a shell. |
| T | Argument injection through file names that begin with `-` or contain wildcards. | `--` end-of-options handling. Names are never expanded as patterns unless requested. All paths go through Core normalisation. |
| R | No record of what a scripted run did. | The CLI uses the same journal as the apps. Exit codes are stable and documented in --help. History uses the journal's bounded, checksum-validating reader without truncating a damaged tail or retaining per-file state. Moves and automatic replacements show a dry-run preview and require confirmation (prompt or --yes). Resume uses the engine's confirmation callback, which shows the saved sources, destination and mode plus every risky saved option in plain words (move, replace rules, follow links, verify off, copy permissions); a saved job that moves or replaces files first gets the same dry-run preview as `copy`, and the resume is refused (even with --yes) if the saved job changed between the preview and the question. A portable install adds a warning that other people may be able to change its saved jobs. |
| I | Verbose output or crash dumps leak paths or secrets. | User-controlled output goes through the Core scrubber; control characters and invisible format characters (text-direction overrides and isolates, zero-width characters, byte-order marks: Unicode category Cf) are shown as spaces, so a file name cannot reorder or hide what a person confirms. JSON uses source-generated serialization. Exceptions produce plain messages, never stack traces. Local logs use LogSetup and record only command, result and exception type. |
| D | Pathological arguments or response files cause runaway memory or time. | At most 4,096 arguments, each at most 32,767 characters; control characters rejected. Response-file expansion and parser directives are disabled. History streams bounded journal lines with cancellation. Console reads cannot prevent cancellation. |
| E | The CLI is run elevated by habit and acts with more rights than needed. | Every copy, move and resume goes through the engine's elevation refusal. There is no force-elevation override. |

### Build and release pipeline (TB8)

| STRIDE | Threat | Mitigation |
|--------|--------|------------|
| S | A malicious or typosquatted dependency or action. | Central package management with lock files (`--locked-mode` in CI, and CI fails if a lock file is missing; the release's `dotnet publish` runs with `--no-restore` after the locked build). `nuget.config` clears every machine and user feed and maps every package id to nuget.org only (package source mapping). Actions pinned by full commit SHA. Dependabot proposes updates for review, with a 7-day cooldown so a hijacked new version is usually pulled before it is proposed. Each new dependency is justified in its PR. Every release ships a CycloneDX SBOM, covered by the same provenance attestation as the zip, so the dependency set can be audited after the fact. The CycloneDX tool is pinned by version, not by hash (see Accepted risks); it runs only in the build job, which has no secrets. |
| S | A release binary is replaced or forged after the build, or a compromised build step steals the signing key. | Release binaries are Authenticode-signed (SHA-256, timestamped) and `build.ps1 -Sign` fails unless every signature is `Valid`. The release zip and the SBOM carry a GitHub build provenance attestation (`actions/attest-build-provenance`) that ties them to the workflow run and commit. Isolation is per job, not per step, because a runner holds every secret its job references for the whole job: the `build` job (read-only token, no environment, no secrets) restores, builds, tests, publishes and makes the SBOM, then uploads them with a SHA-256 manifest whose own hash is passed as a job output. The `release` job runs on a fresh runner in the `release` environment, where the signing secrets live; it runs no restore, build, test or dotnet tool, only first-party GitHub actions (checkout, download-artifact, attest-build-provenance) and repository scripts. It refuses to continue unless the manifest's hash matches the build job's output and the downloaded files match the manifest exactly (no changed, missing or extra file). Only its `Sign` step sees the secrets (step-level `env`), and it runs only `build.ps1 -SignOnly`. In that step the PFX is imported into the runner's user store and the public certificate is added to the runner's machine Root store so the strict `Valid` check passes. Both certificates and the PFX file are removed in a `finally` block. The runner is ephemeral and the machine-wide trust is refused outside GitHub Actions. |
| T | A compromised workflow alters the build or pushes code, or uses the job's OIDC token to get provenance for its own artifact. | Workflow tokens are read-only by default (`permissions: {}` at the top of the release workflow). Write scopes are granted per job only where needed: `security-events` on the CodeQL job, and `contents`, `id-token` and `attestations` (write) on the release workflow's `release` job only. `id-token: write` exposes the OIDC request token to every step of its job, so that job runs no build or test code: a compromised dependency in the `build` job has neither the token nor `contents: write`. `persist-credentials: false` on checkout. Branch protection on `main`: PR required, CI and CodeQL required, no force push or deletion. |
| E | Anyone with push access creates a `v*` tag on an unreviewed commit or branch and gets a signed release. | The build job first requires the tagged commit to be an ancestor of `origin/main` (reviewed PR path), and the release job needs the build job. The signing secrets sit in the `release` environment, whose deployment rule only admits `v*` tags. A tag ruleset on `v*` blocks deletion, update and non-fast-forward (no re-pointing a released tag). An old commit on `main` can still be tagged and released (see Accepted risks). **The main-ancestry check is not a security control on its own:** a tag push runs `release.yml` as it exists at the tagged commit, so someone with push access can push a branch whose workflow drops the check, tag it `v*`, and still reach the signing secrets and the OIDC token. What actually stops that is owner settings in GitHub, which no script in the repository can enforce: a required reviewer on the `release` environment, tag protection (a ruleset) that restricts who can create `v*` tags, and the `EVERYAPP_SIGN_*` values stored as `release` environment secrets, never as repository secrets (a repository secret would be reachable from any branch's workflow). |
| S | The self-signed signing key leaks (repository secret, developer PC, PFX file), so an attacker can sign malware that this PC's users trust. | The PFX is password-protected (AES256, at least 16 characters), git-ignored, and secrets are only set by the user, never by script. After the PFX is exported, `New-SigningCert.ps1` puts the certificate back in the user store with a non-exportable key, so the PFX is the only exportable copy. Trust is limited to the current user on the dev PC. Recovery: run `New-SigningCert.ps1 -Rotate` (creates the new certificate first, removes the old from all stores last), update the local thumbprint and the `release` secrets, and publish a notice. Updaters (M2+) pin the certificate, so a rotation ships as a signed update from the new key or a manual reinstall. |
| I | Secrets or personal details committed to the public repo. | GitHub secret scanning and push protection. No secrets, personal paths, user names, this PC's drive letters or machine names in committed files: task cards use `<worktree>`/`<repo>` placeholders, pasted build output is cleaned before commit, and `git grep -nIE "Obsidian|\\Users\\|/Users/"` should find nothing outside `.agents/log.jsonl` (the owner's file, reviewed separately). Local-only config is git-ignored. |
| D | Pipeline abuse for compute. | Timeouts on jobs. CI uses a concurrency group that cancels superseded runs; the release workflow uses a per-tag group that never cancels a running release. |
| E | A pull request from a fork runs with write access. | No `pull_request_target` triggers. Fork PRs get a read-only token. |

### Developer tooling (not shipped)

Run by the developer on their own PC. None of it is in `EveryApp.slnx`'s shipped output, the release zip, the SBOM or the signed set.

| Tool | Threat | Mitigation |
|------|--------|------------|
| `bench.ps1` (speed comparison) | Empties the wrong folder (the source, a drive root, a user folder) or follows a link while clearing a destination. | Only empties a folder it made or marked (marker file), never a drive root, refuses a destination that is the source or inside or around it, and removes links as links. The overlap check compares paths as text, so a junction can hide an overlap; the marker rule still stops it from emptying anything it did not make (see Accepted risks). Runs unelevated (ferry refuses to run elevated); the standby-cache flush is a separate administrator step. |
| `Ferry.Bench` (benchmark tool: `flush`, `sweep`, `jobs`, `generate`, `micro`) | `flush` enables `SeProfileSingleProcessPrivilege` and calls `NtSetSystemInformation`, so it runs as administrator. `sweep` and `jobs` delete folders. | `flush` does only that one call and nothing else with the privilege. `sweep` uses the same marker-file rule as `bench.ps1` and deletes links as links; `jobs` deletes only the run folders it created under its own jobs folder. The source/destination check is text only (as above). Not signed, not released, not in the SBOM. |
| `soak.ps1` (hours-long copy/move/kill/resume loop) | Empties the wrong folder, or suspends and kills the wrong process. | Refuses to run as administrator. Only empties DestRoot and MoveRoot, each only when new, empty or marked by the script; never a drive root, never under a link, links removed as links, refuses a root that is the source or inside or around it (text compare, as above). The source is only read. It suspends and kills only the `ferry.exe` process it started itself. |
| `scripts/New-SigningCert.ps1` | The signing key is copied out of the user store, or a weak PFX password lets a stolen PFX be opened. A new certificate is trusted in the user's Root store. | Password of at least 16 characters, asked twice. After the PFX export, the store copy is replaced with a non-exportable key. Trust is for the current user only (CurrentUser\Root and TrustedPublisher); Windows shows its own prompt for the Root store. Every step asks first, `-WhatIf` shows them all, and a failure rolls back what the run added. The script never uploads secrets. See the key-leak row above. |
| `spikes/` (Explorer interception prototype: COM registration scripts, native DLL) | A prototype that registers into Explorer ends up in a build or release. | Kept out of `EveryApp.slnx`, the release workflow and the SBOM. `build.ps1` only checks its project for a lock file. Manual use only, following its own test notes. |

## Components designed in M2+

Each row is a binding requirement from spec section 14, to be expanded into full threats and tests when the component is built.

| Component | Status | Mitigations required (from spec section 14) |
|-----------|--------|---------------------------------------------|
| Apps (Ferry, Hullwatch, Stowage and later) | Designed in M2+ | Run non-elevated, never as admin "just in case". All inputs (file names, paths, contents, SMART data, event-log text, feeds, vendor pages, SSH servers, the hosts file, `pyvenv.cfg`) are untrusted and parsed defensively. The hosts-file and `pyvenv.cfg` parsers are fuzz-tested. Destructive actions need a preview and confirmation. Risky features ship off by default behind feature flags. Any network listener binds to localhost unless the user explicitly widens it. Logs are scrubbed of secrets and personal paths. |
| Helper service (SYSTEM) | Designed in M2+ | The only resident, privileged piece. Minimal, versioned, allow-listed command set. Every request is authenticated and validated. No generic "run this" command. Idle budget of about 0% CPU and 40 MB RAM total. |
| Named pipes (apps and helper) | Designed in M2+ | ACLs restricted to the interactive user and SYSTEM. Authenticated, versioned protocol. Pipe messages are untrusted and the protocol parser is fuzz-tested. Reject remote clients. |
| Explorer extension (C++) | Designed in M2+ | Minimal native code, with every mitigation on: CFG, /GS, ASLR and high-entropy, CET shadow stack compatible, Spectre mitigations. No parsing of untrusted data in-process. It hands the operation to the helper over a pipe and returns. Falls back to the stock Windows copy if the helper is unreachable or anything fails. Reviewed line by line. |
| Elevated copy worker | Designed in M2+ | Per-job and short-lived. Revalidates paths. Holds admin rights only for the duration of the job. Same path-safety rules as the Engine. |
| Updater | Designed in M2+ | Packages are signature-checked against the pinned certificate before install. Delta updates are verified the same way. Nothing downloaded is executed without the signature and hash checks the source supports, plus user confirmation. |
| Alert integrations (ntfy, Home Assistant, MQTT, others) | Designed in M2+ | Tokens and credentials stored with DPAPI or Credential Manager, never in plain settings files or logs. TLS for all transport. Alert payloads are scrubbed of personal paths and secrets. Outbound only. |
| Feed downloads (vulnerability feeds, vendor pages) | Designed in M2+ | Downloaded over TLS with integrity checks where the source provides them. Feed files, and local config files read during scans (hosts file, `pyvenv.cfg`), are parsed defensively and fuzz-tested. Vendor-page scraping never auto-installs anything: it only informs. |

## Accepted risks

| Risk | Why accepted |
|------|--------------|
| A process running as the same user swaps files or folders while a job runs (for example after the final-path check of a part file, or between a source's verify and its delete-by-handle mismatch check). | Same-user processes already have every right the job has; the handle-based checks stop redirection to places the user could not reach anyway, and verified deletes never remove a file that changed. |
| Part files are deleted by name in a few places: a failed copy's own part, and on resume the part names the journal recorded. | The names are random (`.<8 hex>.ferrypart`), created with CREATE_NEW by this job, checked to be inside the destination and of Ferry's shape; a collision with a user file is not realistic. Covered: on resume, a journaled part is deleted through a handle opened without following links, and only if its final path is under the destination's final path (a link in the destination or in the journaled path makes it skipped with a plain problem); a recovered target gets the same final-path check before its metadata or permissions are written. Not covered: a failed copy's own part is cleaned up by path (its name is fresh and random), as are the checksum list's and the lost-parts report's own part files, and a same-user process that swaps a link in between the check and the delete (see the first row). The part-name shape and the journal's own folder-match rule are still the only guard against a user file with a name of that exact shape. |
